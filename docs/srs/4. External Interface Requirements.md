## 4. External Interface Requirements

### 4.1 User Interfaces

| Surface | Built with | Screens |
| ------- | ---------- | ------- |
| Extension popup | Vue 3 (shared components with the dashboard) | Status bar · tabs from other browsers (open and recently closed) · history search (P2) |
| Extension options page | Vue 3 | Account · devices · modules · exclusions · retention · bookmark snapshots · export · about |
| Extension onboarding | Vue 3, opened on install | Welcome · create, sign in or recover · username and passphrase · recovery key · choose modules |
| Address-bar keyword | `omnibox` API | `tz <query>` → history suggestions |
| Web dashboard | Vue 3 SPA | Sign in · Overview · Tabs · History · Bookmarks · Extensions · Settings |

Common rules:

- Follow the system light or dark theme. Meet WCAG 2.1 AA contrast. Everything must work by keyboard.
- Error messages say what happened, whether data is safe, and what to do next. Never show a bare HTTP status code.
- All UI strings come from locale files (see [section 6.3](<6. Other Requirements.md#63-internationalization>)). Layouts must work right-to-left.

### 4.2 Hardware Interfaces

None. Tazamun only uses browser and network APIs.

### 4.4 Communications Interfaces

#### 4.4.1 General

- HTTPS only (plain HTTP accepted only for `localhost`). JSON bodies, UTF-8. All binary values in base64url.
- Version prefix `/v1`. Breaking changes require `/v2`. The server reports `minClientVersion` in `/v1/info`.
- Authentication: `Authorization: Bearer <session token>`. Tokens are random 256-bit values that the server stores hashed. One session per device.
- Errors: `{"error": {"code": "QUOTA_EXCEEDED", "message": "...", "retryAfter": 30}}`. Error codes are stable and documented.
- CORS: allow the dashboard's own origin. Extension origins are allowed through host permission for the server URL.
- Limits: request body ≤ 2 MB, ≤ 500 records per batch, rate limits per account and per IP.

#### 4.4.2 Record envelope

```jsonc
{
  "id": "b64url, ≤ 64 chars",      // GUID, device ID, or HMAC of the URL (history)
  "seq": 18234,                    // assigned by the server, increases monotonically per account
  "modifiedAt": "2026-11-24T10:00:00Z", // server time; informational only, never used for merging
  "expiresAt": "2027-11-24T00:00:00Z",  // optional; the server deletes the record after this time
  "payload": "b64url(nonce(12) || ciphertext || tag(16))"
}
```

The decrypted payload is JSON: `{"v": <schemaVersion>, "deleted": false, "hlc": "...", "data": {...}}`. `hlc` is the [Hybrid Logical Clock](../adr/0003-sync-protocol-records-hlc.md) stamp of the record's last change, serialized as `<wall time in ms, 15 decimal digits>:<counter, 8 lowercase hex digits>:<device ID>` (for example `001795000000000:000000ff:dev_A-1`). The fields are fixed-width, so stamps sort correctly as plain strings. Modules that merge per field (bookmarks) store one such stamp per field inside `data`. Deletions are encrypted tombstones (`"deleted": true`). The server can't tell a tombstone from any other record. It removes tombstones after `expiresAt`, which clients set to 90 days.

- **Tombstones** have no `data`: `{"v": 1, "deleted": true, "hlc": "..."}`.
- **`v`** is the collection's major schema version (ENG-10). It changes only for breaking changes. Adding an optional field doesn't change it, and clients must keep fields they don't know and push them back unchanged, so an older client never strips data written by a newer one.
- **Payload data per collection** is defined by the zod schemas in `packages/core/src/schema/collections/`: `tabs` (TAB-1, TAB-2, TAB-4), `history` (HIS-2) and `extensions` (EXT-1, EXT-2). The `bookmarks` schema will be defined in P4. Device names are not a collection: they are plaintext in the device API ([ADR-0009](../adr/0009-device-names-and-key-storage.md)).

#### 4.4.3 Endpoints

| Method and path | Purpose | Auth |
| --------------- | ------- | ---- |
| `GET /v1/info` | Server version, `minClientVersion`, registration mode, limits; when signed in, the high-water `seq` per collection and storage used | optional |
| `GET /v1/health` | Liveness check | none |
| `POST /v1/accounts` | Create an account: `accountId`, `username`, `salt`, `kdfParams`, `authHash`, `wrappedAccountKey`, `recoveryAuthHash`, `recoveryWrappedAccountKey`, optional invite token | none |
| `POST /v1/prelogin` | `{username}` → `accountId`, `salt` and `kdfParams` (for unknown usernames, fake but stable values, so the response doesn't reveal whether the username exists) | none |
| `GET /v1/accounts/me` | `accountId`, `username` (null for accounts from before usernames) and whether a recovery key is set | yes |
| `PUT /v1/accounts/me/username` | Set or change the username (`409 USERNAME_TAKEN` if another account has it) | yes |
| `PUT /v1/recovery` | Set or replace the recovery key: `recoveryAuthHash`, `recoveryWrappedAccountKey` (needs the current `authKey`) | yes |
| `POST /v1/recovery/key` | `{username, recoveryAuthKey}` → `accountId` and the account key wrapped under the recovery key | none |
| `POST /v1/recovery/passphrase` | `{username, recoveryAuthKey}` plus a new `salt`, `kdfParams`, `authHash`, `wrappedAccountKey`; ends every session | none |
| `POST /v1/sessions` | Sign in with `accountId` and `authKey`, plus device ID and name → session token | none |
| `DELETE /v1/sessions/current` | Sign out this device | yes |
| `GET /v1/keys` · `PUT /v1/keys` | Read the wrapped key bundle · re-wrap after a passphrase change (needs the current `authKey`) | yes |
| `GET /v1/devices` · `PUT /v1/devices/{id}` · `DELETE /v1/devices/{id}` | List, rename, or revoke devices (revoking ends that device's sessions) | yes |
| `GET /v1/collections/{name}?since={seq}&limit={n}` | Incremental pull → `{records, nextSince, more}` | yes |
| `POST /v1/collections/{name}` | Batch upsert `[{id, payload, expiresAt?}]` → `[{id, seq}]` | yes |
| `DELETE /v1/accounts/me` | Delete the account and all data | yes (+ `authKey`) |

The server compares `authKey` and `recoveryAuthKey` hashes in constant time, rate-limits sign-in, prelogin, registration and both recovery endpoints, and never logs request bodies.

Behaviour clients rely on:

- `seq` is one counter per account, shared by all collections. It never decreases, even after records expire.
- A push is stored completely or not at all (REL-4). A batch that names the same record ID twice is rejected. A push that would exceed the storage quota is rejected as a whole; a push that reduces storage is always accepted, so a full account can still write tombstones.
- A pull returns at most `limit` records (default and maximum 500) and stops early at about 2 MiB of payload, but always returns at least one record when one is left. `nextSince` is the `seq` of the last record returned (or `since` when none were). Expired records are never returned.
- `/v1/info` with an invalid token answers `401` rather than falling back to the anonymous response, so a revoked device learns it's signed out (ENG-9).
- Signing in again with the same device ID replaces that device's session token.

#### 4.4.4 Error codes

Codes are stable: clients branch on them, so a code is never renamed or reused, only added. The list is `schema.ERROR_CODES` in `packages/core`. Messages are for people and may change.

| Code | HTTP | Meaning |
| ---- | ---- | ------- |
| `INVALID_REQUEST` | 400 | The body, a parameter or the query doesn't match the schema. The message names the fields, never their values. |
| `UNAUTHORIZED` | 401 | No session token, or it has ended (signed out, device revoked, passphrase changed elsewhere). Treat as signed out. |
| `INVALID_CREDENTIALS` | 401 | Wrong account ID, auth key, username or recovery key. The same answer for each, so it doesn't reveal which accounts exist. |
| `REGISTRATION_CLOSED` | 403 | The server accepts no new accounts. |
| `INVITE_REQUIRED` | 403 | The server is in `invite` mode and the request has no invite token. |
| `INVITE_INVALID` | 403 | The invite token is unknown, already used or expired. |
| `QUOTA_EXCEEDED` | 403 | The batch would take the account over its storage quota. Nothing from it was stored. |
| `NOT_FOUND` | 404 | No such endpoint, or no such device in this account. |
| `ACCOUNT_EXISTS` | 409 | An account with this ID already exists. |
| `USERNAME_TAKEN` | 409 | Another account on this server has this username. |
| `PAYLOAD_TOO_LARGE` | 413 | The request body is over 2 MiB. |
| `RATE_LIMITED` | 429 | Too many requests. `retryAfter` and the `Retry-After` header say how many seconds to wait. |
| `INTERNAL` | 500 | An unexpected server error. Retry with backoff. |
| `UNAVAILABLE` | 503 | The server can't reach its database (`/v1/health`). |
