## 4. External Interface Requirements

### 4.1 User Interfaces

| Surface | Built with | Screens |
| ------- | ---------- | ------- |
| Extension popup | Vue 3 (shared components with the dashboard) | Status bar · tabs from other browsers · send this tab · history search (P2) |
| Extension options page | Vue 3 | Account · devices · modules · exclusions · retention · bookmark snapshots · export · about |
| Extension onboarding | Vue 3, opened on install | Welcome · create or connect · passphrase · recovery kit · choose modules |
| Address-bar keyword | `omnibox` API | `tz <query>` → history suggestions |
| Context menu | `contextMenus` / `menus` API | Send page or link to device |
| Web dashboard | Vue 3 SPA | Sign in · Overview · Tabs · History · Bookmarks · Extensions · Settings |

Common rules:

- Follow the system light or dark theme. Meet WCAG 2.1 AA contrast. Everything must work by keyboard.
- Error messages say what happened, whether data is safe, and what to do next. Never show a bare HTTP status code.
- All UI strings come from locale files (see [section 6.3](<6. Other Requirements.md#63-internationalization>)). Layouts must work right-to-left.

### 4.2 Hardware Interfaces

None. Tazamun only uses browser and network APIs.

### 4.3 Software Interfaces

#### 4.3.1 Browser APIs per module

| Module | APIs | Differences between Chrome/Edge and Firefox that matter |
| ------ | ---- | ------------------------------------------------------- |
| Engine | `storage`, `alarms`, `runtime`, IndexedDB, Web Crypto | Chrome MV3 uses a **service worker** that is shut down after about 30 s idle; Firefox MV3 uses a non-persistent **event page**. Chrome's minimum alarm period is 30 s. `storage.local` is limited to 10 MB without `unlimitedStorage`. |
| Tabs | `tabs`, `windows`, `tabGroups` (where available), `notifications` | Tab group APIs differ between Chromium and Firefox; group titles are best effort. Firefox refuses `tabs.create` for privileged URLs (`about:*` and others), and `file:` URLs are restricted. |
| History | `history`, `omnibox` | Chrome's `history.addUrl` takes only a URL (no title or visit time), which is one reason synced history isn't written back ([ADR-0005](../adr/0005-history-stored-in-extension.md)). `onVisitRemoved` reports `allHistory: true` when a browser's history is cleared. |
| Bookmarks | `bookmarks` | Different root IDs (Chromium: `"1"` bar, `"2"` other, `"3"` mobile; Firefox: `toolbar_____`, `menu________`, `unfiled_____`, `mobile______`). Roots are read-only. Chromium has no separators. Firefox tags and keywords aren't exposed. Enterprise policies can add read-only managed bookmarks. Event order during bulk changes is not guaranteed. |
| Extensions | `management` | `management.getAll()` is available on both. Firefox reports add-on IDs (e.g. `name@domain` or `{uuid}`), not store slugs; map them to Firefox Add-ons pages via the equivalence file or the AMO lookup API (verify behaviour before relying on it). |
| UI | `contextMenus` (Chromium) / `menus` (Firefox), `action`, `notifications` | WXT and the `browser` polyfill hide most naming differences. |

### 4.4 Communications Interfaces

#### 4.4.1 General

- HTTPS only (plain HTTP accepted only for `localhost`). JSON bodies, UTF-8. All binary values in base64url.
- Version prefix `/v1`. Breaking changes require `/v2`. The server reports `minClientVersion` in `/v1/info`.
- Authentication: `Authorization: Bearer <session token>`. Tokens are random 256-bit values that the server stores hashed. One session per device.
- Errors: `{"error": {"code": "QUOTA_EXCEEDED", "message": "...", "retryAfter": 30}}`. Error codes are stable and documented.
- CORS: allow the dashboard's own origin. Extension origins are allowed through host permission for the server URL.
- Limits: request body ≤ 2 MB, ≤ 500 records per batch, rate limits per account and per IP.

#### 4.4.2 Record envelope

```jsonc
{
  "id": "b64url, ≤ 64 chars",      // GUID, device ID, or HMAC of the URL (history)
  "seq": 18234,                    // assigned by the server, increases monotonically per account
  "modifiedAt": "2026-11-24T10:00:00Z", // server time; informational only, never used for merging
  "expiresAt": "2027-11-24T00:00:00Z",  // optional; the server deletes the record after this time
  "payload": "b64url(nonce(12) || ciphertext || tag(16))"
}
```

The decrypted payload is JSON: `{"v": <schemaVersion>, "deleted": false, "hlc": "...", "data": {...}}`. `hlc` is the [Hybrid Logical Clock](../adr/0003-sync-protocol-records-hlc.md) stamp of the record's last change, serialized as `<wall time in ms, 15 decimal digits>:<counter, 8 lowercase hex digits>:<device ID>` (for example `001795000000000:000000ff:dev_A-1`). The fields are fixed-width, so stamps sort correctly as plain strings. Modules that merge per field (bookmarks) store one such stamp per field inside `data`. Deletions are encrypted tombstones (`"deleted": true`). The server can't tell a tombstone from any other record. It removes tombstones after `expiresAt`, which clients set to 90 days.

- **Tombstones** have no `data`: `{"v": 1, "deleted": true, "hlc": "..."}`.
- **`v`** is the collection's major schema version (ENG-10). It changes only for breaking changes. Adding an optional field doesn't change it, and clients must keep fields they don't know and push them back unchanged, so an older client never strips data written by a newer one.
- **Payload data per collection** is defined by the zod schemas in `packages/core/src/schema/collections/`: `tabs` (TAB-1, TAB-4), `commands` (TAB-7), `history` (HIS-2) and `extensions` (EXT-1, EXT-2). The `bookmarks` (P4) and `devices` (after Q2) schemas will be defined in their phases.

#### 4.4.3 Endpoints

| Method and path | Purpose | Auth |
| --------------- | ------- | ---- |
| `GET /v1/info` | Server version, `minClientVersion`, registration mode, limits; when signed in, the high-water `seq` per collection and storage used | optional |
| `GET /v1/health` | Liveness check | none |
| `POST /v1/accounts` | Create an account: `accountId`, `salt`, `kdfParams`, `authHash`, `wrappedAccountKey`, optional invite token | none |
| `GET /v1/accounts/{id}/prelogin` | Returns `salt` and `kdfParams` (for unknown IDs, returns fake but stable values so the response doesn't reveal whether the account exists) | none |
| `POST /v1/sessions` | Sign in with `accountId` and `authKey`, plus device ID and name → session token | none |
| `DELETE /v1/sessions/current` | Sign out this device | yes |
| `GET /v1/keys` · `PUT /v1/keys` | Read the wrapped key bundle · re-wrap after a passphrase change (needs the current `authKey`) | yes |
| `GET /v1/devices` · `PUT /v1/devices/{id}` · `DELETE /v1/devices/{id}` | List, rename, or revoke devices (revoking ends that device's sessions) | yes |
| `GET /v1/collections/{name}?since={seq}&limit={n}` | Incremental pull → `{records, nextSince, more}` | yes |
| `POST /v1/collections/{name}` | Batch upsert `[{id, payload, expiresAt?}]` → `[{id, seq}]` | yes |
| `DELETE /v1/accounts/me` | Delete the account and all data | yes (+ `authKey`) |

The server compares `authKey` hashes in constant time, applies a rate limit to `POST /v1/sessions`, and never logs request bodies.
