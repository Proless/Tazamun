## 3. Software Features

Each feature has a description, its priority and phase, stimulus/response sequences, and numbered functional requirements. Priorities: **M** = Must, **S** = Should, **C** = Could. Phases P0–P6 refer to the roadmap in [`CLAUDE.md`](../../CLAUDE.md).

### 3.1 Account, Pairing and Devices

**Description:** A server hosts any number of accounts, for example a family, friends or a small team on one instance (ADM-2, ADM-3). Accounts are isolated from each other and from the operator: each has its own passphrase and keys. A person needs one account per server, connects any number of browsers (devices) to it, and manages those devices. There's no email address: people sign in with a **username** and a passphrase, and the account is identified internally by a random account ID ([ADR-0010](../adr/0010-usernames-and-recovery-key.md)). A browser profile is connected to one account at a time; someone who wants two accounts in the same browser (work and personal) uses one browser profile per account. **Priority:** High. **Phase:** P1.

**Stimulus/response:**

1. The user installs the extension and chooses *Create account*. The extension asks for the server URL, a username and a passphrase (entered twice), generates the account ID, account key and recovery key, derives keys, registers the account, and shows the **recovery key** once, to download, print or copy.
2. On a second browser the user chooses *Sign in to an existing account* and enters the server URL, the username and the passphrase. The extension signs in, unwraps the account key, registers itself as a device and starts the first sync.
3. A user who forgot the passphrase chooses *Forgot your passphrase?* there instead, enters the recovery key and a new passphrase. Every other browser is signed out and signs in again with the new passphrase.
4. In the dashboard the user revokes a lost device. Its session ends and it stops syncing.

| ID | Requirement | Pri | Phase |
| -- | ----------- | --- | ----- |
| ACC-1 | The client shall generate a random 128-bit account ID and a random 256-bit account key on account creation. The account ID identifies the account internally and is bound into every key and record; people never need to type it. | M | P1 |
| ACC-2 | The client shall derive a 512-bit output with Argon2id from the passphrase and a random per-account salt, and split it into an **auth key** and a **KEK** (see [section 5.2](<5. Other Nonfunctional Requirements.md#52-security-requirements>)). | M | P1 |
| ACC-3 | The server shall store only the salt, the KDF parameters, a SHA-256 hash of the auth key, and the account key wrapped by the KEK. It shall never receive the passphrase, the KEK or the account key. | M | P1 |
| ACC-4 | The client shall require a passphrase of at least 12 characters and show a strength estimate. It shall state, before the account is created, that losing both the passphrase and the recovery key means lost data. | M | P1 |
| ACC-5 | The client shall generate a **recovery key** (160 random bits) at account creation and show it once for download, printing or copying; it shall never be stored. With the username, it shall let the user set a new passphrase without the old one, which ends every session. A signed-in device shall be able to replace it (the old one stops working). Format: [ADR-0010](../adr/0010-usernames-and-recovery-key.md). | M | P1 |
| ACC-6 | *Removed* (ADR-0010): the pairing code carried the account ID, which the username (ACC-13) replaces. Pairing a browser from a signed-in one may return as a new requirement. | – | – |
| ACC-7 | Each device shall register with a random device ID, a user-editable name (default: browser name, OS, profile), and the browser family and version. | M | P1 |
| ACC-8 | Each device shall hold its own session token. Revoking a device shall invalidate its token on the server immediately. | M | P1 |
| ACC-9 | Changing the passphrase shall only re-wrap the account key. Stored data shall not be re-encrypted. Other devices shall be required to sign in again. | S | P3 |
| ACC-10 | Deleting the account shall delete every record, key bundle and session on the server. | M | P3 |
| ACC-11 | The extension shall show a clear signed-out state and keep local data until the user chooses to remove it. | M | P1 |
| ACC-12 | A browser profile shall be connected to at most one account. Before a profile that was connected to one account is connected to another, the extension shall say that this replaces the previous account's data on this browser, and that a separate browser profile keeps both. | S | P1 |
| ACC-13 | Each account shall have a **username**, unique per server: 3–32 characters, lowercase ASCII letters, digits, `.`, `_` and `-`, starting and ending with a letter or digit. Clients shall normalize input (NFKC, trimmed, lowercase). Signing in shall take the server URL, the username and the passphrase. The username shall be changeable; renaming shall not touch encrypted data. | M | P1 |

Notes:

- **Server URL:** HTTPS, or plain HTTP for `localhost`, `127.0.0.1` and `[::1]` only (SRS 4.4.1). Input without a scheme gets `https://`, or `http://` for those loopback hosts. No credentials, query or fragment. The host permission is requested for that host only.
- **Usernames (ACC-13):** the operator can read them, like device names (ADR-0009). Prelogin doesn't reveal whether a username exists (SEC-9); registering does (`USERNAME_TAKEN`), which a unique name can't avoid. Accounts created before usernames existed set one from a signed-in browser's options page.
- **Recovery key (ACC-5):** 32 Crockford base32 characters in groups of four (`ABCD-EFGH-…`); case, spaces and dashes don't matter. With the username it opens the account, so the UI says to keep it as safe as the passphrase. Accounts created before it existed are asked to make one.
- **Strength estimate (ACC-4):** informs and never blocks a passphrase of 12 or more characters.
- **Signed-out states (ACC-11):** *signed out* by the user, or *revoked* when the server rejects the token. Both keep the server URL, account ID, username, device ID and local data, so signing in again needs only the passphrase; the device ID stays the same. *Revoked* also covers a passphrase change or recovery on another device, which ends every other session. *Locked* (SEC-5) means signed in, with the key not remembered.

### 3.2 Sync Engine

**Description:** The engine is shared by all modules. It handles encryption, the outbox, pulling and pushing, scheduling, retries and the merge contract. It knows nothing about any specific data type. **Priority:** High. **Phase:** P1.

**Stimulus/response:**

1. A module reports changed records. The engine encrypts them, stores them in the outbox, and pushes them after a short debounce.
2. An alarm fires or the popup opens. The engine calls `GET /v1/info`, compares each collection's high-water mark with the last seq it has seen, and pulls only collections that changed.
3. The network drops during a push. The outbox entries stay put and are retried with exponential backoff.

| ID | Requirement | Pri | Phase |
| -- | ----------- | --- | ----- |
| ENG-1 | The engine shall define a module interface: `collection` (whose schema carries the `schemaVersion`), `detectLocalChanges(ctx)` (the context gives read access to the engine's mirror and the device ID), `merge(local, remote)`, `apply(records)`, and `snapshot()` (optional, from P4). See [ADR-0001](../adr/0001-one-product-module-architecture.md) and `apps/extension/src/engine/module.ts`. | M | P1 |
| ENG-2 | The engine shall encrypt each record payload with AES-256-GCM, using a fresh 96-bit random nonce and AAD = `accountId \| collection \| recordId`. Decryption shall reject records whose AAD doesn't match. | M | P1 |
| ENG-3 | The engine shall keep a durable outbox in IndexedDB. A record leaves the outbox only after the server confirms it. | M | P1 |
| ENG-4 | The engine shall push local changes after a debounce (default 2 s) and batch up to 500 records or 1 MB per request. | M | P1 |
| ENG-5 | The engine shall poll `GET /v1/info` on an alarm (default 60 s, never below the browser minimum), when the popup or dashboard opens, and on startup. | M | P1 |
| ENG-6 | The engine shall pull incrementally with `since=<last seen seq>` per collection and page through results. | M | P1 |
| ENG-7 | The engine shall keep a Hybrid Logical Clock per device and stamp every locally changed field with it. | M | P1 |
| ENG-8 | When the merge result differs from the server copy, the engine shall push the merged record again. | M | P1 |
| ENG-9 | The engine shall retry failed requests with exponential backoff and jitter (1 s up to 15 min), and treat HTTP 401 as "signed out", not as a retryable error. | M | P1 |
| ENG-10 | The engine shall support a schema version per module. Records with a newer major version than the client understands shall be kept but not applied, and the user shall be told to update. | M | P1 |
| ENG-11 | The engine shall survive the background context being suspended at any point without losing or duplicating changes (idempotent apply, outbox replay). | M | P1 |
| ENG-12 | The user shall be able to pause or resume all sync, and turn sync on or off per module per device. | M | P1 |
| ENG-13 | The engine shall expose a status (idle, syncing, paused, offline, error with reason, last successful sync per collection) to the UI. | M | P1 |
| ENG-14 | The engine shall never write plaintext payloads, keys or URLs to logs. | M | P1 |
| ENG-15 | The engine shall warn the user when the device's clock differs from the server's by more than **5 minutes** (measured at each `GET /v1/info`, against the middle of the request), saying by how much and which way. It shall also warn when a record carries a time more than 24 h in the future; such a record is applied, but its time is not adopted (ENG-7). | S | P1 |
| ENG-16 | When the server's data generation (`/v1/info`) differs from the one last seen, the server was restored from a backup. The engine shall then pull every collection again from the start, merge as usual (newer local versions are pushed back, ENG-8), and push back every record it has that the server lacks, without deleting anything locally. The new generation is stored only after all collections are done. | M | P1 |

### 3.3 Tabs

**Description:** Each device publishes its open windows and tabs, and those of private windows only if the user turns that on, plus the tabs it closed recently. Every other device and the dashboard can see them and open them. Tabs are **not** opened automatically in other browsers. **Priority:** High. **Phase:** P1.

**Stimulus/response:**

1. The user opens, closes or navigates tabs. After a debounce the device's tabs record is updated; closed tabs move to its *Recently closed* list, also when the last window closes.
2. The user opens the popup and sees *Tabs on other browsers*, grouped by device and window, with when each device was last seen: *Open now* for a browser seen in the last 10 minutes, *Open when last seen* for one that isn't, and a collapsed *Recently closed* list. While the popup is open, changes appear without reopening it. Clicking a tab opens it locally.

| ID | Requirement | Pri | Phase |
| -- | ----------- | --- | ----- |
| TAB-1 | Each device shall publish one `tabs` record (record ID = device ID) containing its windows and, per tab: URL, title, pinned, active and last accessed; and its recently closed tabs (TAB-10). Tab groups are not synced. | M | P1 |
| TAB-2 | Tabs from private or incognito windows shall be published only when the user turned on *Include private windows* for tabs on that device (off by default) and the browser allows the extension in private windows. They shall be marked as private, and other devices shall label them so. | M | P1 |
| TAB-3 | URLs matching the user's exclusion list, and privileged or local schemes (`chrome:`, `edge:`, `about:`, `moz-extension:`, `chrome-extension:`, `file:`, `data:`, `blob:`), shall be dropped or shown as non-openable. | M | P1 |
| TAB-4 | `data:` favicons shall be stripped. Only favicon URLs of at most 512 characters shall be kept. | M | P1 |
| TAB-5 | Tab updates shall be debounced (default 5 s) and skipped when nothing relevant changed. | M | P1 |
| TAB-6 | The popup shall list other devices' tabs with the device name and last-seen time, split into open tabs (TAB-11) and recently closed tabs (TAB-10), and let the user open one tab, or all tabs of a window. | M | P1 |
| TAB-7 | *Removed* ([ADR-0011](../adr/0011-private-browsing-choice-and-no-send-tab.md)): send tab to device. | – | – |
| TAB-8 | If the browser refuses to open another device's tab (e.g. privileged pages in Firefox), the client shall copy the URL to the clipboard and say why. | S | P1 |
| TAB-9 | Devices not seen for longer than a configurable period (default 30 days) shall be collapsed and labelled as stale. | S | P3 |
| TAB-10 | A tab that was open on a device and is no longer open, including when its window or the last window closes, shall move to that device's *Recently closed* list with the time it closed. The list shall keep each URL once (the newest), at most **50** tabs, for at most **7 days**; a URL that is open again shall leave it. Exclusions, TAB-3 and TAB-2 shall apply to it as to open tabs. | M | P1 |
| TAB-11 | A device not seen for more than **10 minutes** shall have its tabs shown as *open when last seen*, not as open now. | M | P1 |

Notes:

- **TAB-1:** `lastAccessed` is published where the browser reports it. Tab groups (titles, colours, membership) are out of scope: the `tabGroups` APIs differ between Chromium and Firefox and would need another permission.
- **TAB-3:** privileged, local and excluded URLs are dropped, not shown as non-openable, so nothing about them leaves the device. Only `http:`, `https:` and `ftp:` URLs are synced; unknown schemes stay on the device too. A window left with no tabs is not published.
- **Exclusion patterns (PRIV-3):** host based. `bank.example` covers the host and its subdomains (a leading `*.` or `www.` is ignored), and `notes.example/private` covers only paths starting with `/private`. Matching ignores case, the scheme and the port. The same list will apply to history (HIS-5).
- **TAB-4:** besides `data:` icons and those over 512 characters, favicons that aren't `https:` are dropped. The popup shows no favicons: loading them from the sites would be a third-party request (PRIV-4).
- **TAB-6:** device names and last-seen times come from `GET /v1/devices` (ADR-0009). Records of devices that are no longer on the account (revoked) are hidden.
- **TAB-2:** the switch is per module and per browser (*Include private windows* in the options page). Only the user can allow the extension in private windows (*Allow in Incognito* in Chrome and Edge, *Run in Private Windows* in Firefox); when that is off, the options page says so and where to change it. Exclusions and TAB-3 apply to private windows too. A tab from a private window opens in a normal window on the other device.
- **TAB-8:** in the popup's other tabs list (TAB-6), a refused URL is copied to the clipboard.
- **TAB-10:** a device works the list out itself, by comparing its open tabs with its own last record (rule 4: the browser's state is the truth, events only trigger the check); it needs no `sessions` permission. A browser that quits or a computer that goes off can't send anything, so its last open tabs stay on the server and TAB-11 labels them. A tab closed from a private window keeps its private mark; turning private windows off, or excluding a site, removes its entries too.
- **TAB-11:** "seen" is the device's last request to the server (`lastSeenAt`); a running browser checks in every minute.

### 3.4 History

**Description:** Visits from all browsers are merged into one history that's stored **in the extension and the dashboard**, not written into each browser's native history (see [ADR-0005](../adr/0005-history-stored-in-extension.md)). Users search it from the popup, the address bar keyword, and the dashboard. **Priority:** High. **Phase:** P2.

**Stimulus/response:**

1. The user visits a page. The visit is recorded locally and synced as part of that URL's history record.
2. The user types `tz <words>` in the address bar and sees matching pages from all browsers. Choosing one opens it.
3. The user deletes a URL in the dashboard. It disappears from Tazamun everywhere and, if enabled, from each browser's native history.

| ID | Requirement | Pri | Phase |
| -- | ----------- | --- | ----- |
| HIS-1 | Each URL shall map to one record whose ID is `HMAC-SHA256(idKey, normalizedUrl)`, truncated to 128 bits and base64url-encoded, so the same page from different browsers merges without revealing the URL to the server. | M | P2 |
| HIS-2 | A history payload shall contain the URL, the latest title, and a list of visits (device ID, time, transition type) capped at the 50 most recent. Merging shall be a set union of visits, then the cap. | M | P2 |
| HIS-3 | On first enable, the module shall import the native history from the last N days (default 90, configurable) using only `history.search` results (URL, title, last visit, visit count). It shall not call `getVisits` for every URL. | M | P2 |
| HIS-4 | After import, new visits shall be captured with `history.onVisited`. | M | P2 |
| HIS-5 | URLs matching the exclusion list and the schemes in TAB-3 shall be ignored. Visits in private or incognito windows shall be ignored unless the user turned on *Include private windows* for history on that device (PRIV-1). | M | P2 |
| HIS-6 | The module shall **not** write synced visits into the browser's native history. | M | P2 |
| HIS-7 | Records shall carry a server expiry derived from the retention setting (default 1 year). Expired records shall be removed locally and on the server. | M | P2 |
| HIS-8 | Deleting a URL in Tazamun shall create a tombstone. Visits after the deletion time shall create the record again. | M | P2 |
| HIS-9 | When enabled (default: on), a Tazamun deletion shall also remove the URL from each device's native history (`history.deleteUrl`). | S | P2 |
| HIS-10 | Removing a single URL in the browser's native history shall propagate as a Tazamun deletion. **Clearing all history in a browser shall not** wipe synced history. The user shall instead be asked whether to clear this device's visits or everything. | M | P2 |
| HIS-11 | The extension shall provide full-text search over URL and title, with filters by device, browser and date, from the popup and the `tz` address-bar keyword. | M | P2 |
| HIS-12 | Local storage shall use IndexedDB with a search index. Searching 100,000 entries shall return results within 200 ms on a mid-range laptop. | S | P2 |

### 3.5 Bookmarks

**Description:** One bookmark tree is kept in sync across browser families, with safety features that make data loss recoverable. This is the hardest module and is built last of the core types. **Priority:** High. **Phase:** P4.

**Stimulus/response:**

1. The user enables bookmark sync on a browser that already has bookmarks. A snapshot is taken. The user chooses **merge** (default), **use server copy** or **use this browser's copy**, and the trees are reconciled.
2. The user moves a folder in Firefox. Within a minute the same folder moves in Edge.
3. A remote batch would delete 300 bookmarks. Sync pauses and asks the user to confirm or reject.
4. The user restores a snapshot from the options page.

| ID | Requirement | Pri | Phase |
| -- | ----------- | --- | ----- |
| BMK-1 | Each node (folder, bookmark, separator) shall be a record with a random GUID. Fields: kind, parent GUID, title, URL, position key, date added, per-field HLCs, deleted flag. | M | P4 |
| BMK-2 | The module shall keep a local map from Tazamun GUIDs to native IDs for each browser. Native IDs shall never be synced. | M | P4 |
| BMK-3 | Root folders shall map to canonical roots: `toolbar` (Chrome/Edge "Bookmarks bar" / "Favorites bar"; Firefox "Bookmarks Toolbar"), `other` ("Other bookmarks" / "Other Bookmarks"), `mobile`, and `menu` (Firefox only). On Chromium, `menu` shall appear as a folder named "Bookmarks Menu" inside `other`. Native roots shall never be created, renamed or deleted. | M | P4 |
| BMK-4 | Sibling order shall use fractional-index position keys so that moving one node doesn't renumber its siblings. | M | P4 |
| BMK-5 | Conflicts shall resolve per field by HLC (last writer wins). A concurrent edit and delete shall keep the edited node (edit wins over delete). | M | P4 |
| BMK-6 | Concurrent moves that would create a cycle shall be detected. The node with the older move shall go back to its previous parent. If that's impossible, it shall go to `other`. | M | P4 |
| BMK-7 | Nodes whose parent is missing (orphans) shall be placed in a folder `other/Tazamun recovered` and reported. | M | P4 |
| BMK-8 | Separators shall be synced, but not created on Chromium browsers (which don't support them). They shall be preserved for Firefox. | S | P4 |
| BMK-9 | Local changes shall be found by diffing the full native tree against the mirror. Bookmark events shall only schedule that diff. This also catches changes made while the extension wasn't running. | M | P4 |
| BMK-10 | When applying remote changes, the module shall suppress echoes: events caused by its own writes must not be treated as local changes. | M | P4 |
| BMK-11 | The first sync on a device with existing bookmarks shall match local nodes to remote ones by (canonical root path, URL, title) to avoid duplicates, and offer the three modes in stimulus 1. | M | P4 |
| BMK-12 | A full local snapshot shall be taken before the first sync, before applying any batch that deletes or moves more than 10 nodes, and daily. The last 10 snapshots (plus one weekly for 4 weeks) shall be kept and be restorable from the options page. Snapshots shall be exportable as HTML bookmark files. | M | P4 |
| BMK-13 | If a remote batch would delete more than 20% of nodes or more than 50 nodes, the module shall pause bookmark sync and ask the user. | M | P4 |
| BMK-14 | The extension shall warn, once and dismissibly, that keeping the browser's own bookmark sync on alongside Tazamun can create duplicates. | M | P4 |
| BMK-15 | Managed (enterprise-policy) bookmarks and other read-only nodes shall be skipped. | M | P4 |
| BMK-16 | Data that the WebExtension API doesn't expose (e.g. Firefox tags and keywords) is out of scope and shall be documented as a limitation. | M | P4 |

### 3.6 Extension Inventory

**Description:** Each device publishes its installed extensions. The dashboard shows a table of extensions by browser and helps the user install what's missing. Installing extensions programmatically isn't possible; Tazamun only links to stores. **Priority:** Medium. **Phase:** P5.

**Stimulus/response:**

| EXT-2 | Development (unpacked) and admin-installed extensions shall be flagged as such. | S | P5 |

| EXT-6 | The UI may point out that Edge can install from the Chrome Web Store. | C | P5 |
| EXT-7 | Users shall be able to suggest a mapping by opening a pre-filled GitHub issue. | C | P5 |

### 3.11 Self-Hosting, Containers and Image Publishing

**Description:** Running a Tazamun server must take one command. The project ships one official container image, built, tested, scanned and published only by CI, plus ready-to-use deployment files. Self-hosting is the main way Tazamun is used (there is no official hosted service), so this feature is as important as any data type. See [ADR-0007](../adr/0007-container-distribution.md). **Priority:** High. **Phase:** P1 (image, Compose, `edge` builds), P6 (versioned releases, signing, SBOM).

**Stimulus/response:**

1. A self-hoster downloads `docker-compose.caddy.yml`, sets `TAZAMUN_PUBLIC_URL=https://sync.example.org`, and runs `docker compose up -d`. Caddy gets a TLS certificate and Tazamun becomes healthy. The self-hoster runs `docker compose exec tazamun tazamun invite create` and gives the token to a user.
2. A maintainer pushes tag `v1.2.0`. CI builds the image for amd64 and arm64, runs the container smoke tests, scans for vulnerabilities, signs the image, attaches an SBOM and provenance, and publishes `1.2.0`, `1.2`, `1` and `latest`.
3. The self-hoster runs `docker compose pull && docker compose up -d`. The server takes a backup before migrating, migrates, and comes back. Clients keep syncing.
4. The self-hoster runs `docker compose exec tazamun tazamun backup /data/backups/manual.db` and copies the file off-site.

#### Image

| ID | Requirement | Pri | Phase |
| -- | ----------- | --- | ----- |
| DEP-1 | The project shall publish one OCI image containing the server and the built dashboard. Running it shall need no other service (no separate database, cache or queue). | M | P1 |
| DEP-2 | The image shall use a multi-stage build. The runtime stage shall contain only the production server bundle, production dependencies and the dashboard's static files: no compilers, no source maps of dependencies, no package-manager caches. Target size: ≤ 150 MB compressed. | M / S | P1 |
| DEP-3 | The container shall run as a fixed non-root user (UID/GID `10001`, documented) and work with a read-only root filesystem when `/data` is writable (and optionally `/tmp` as tmpfs). | M | P1 |
| DEP-4 | All persistent state (SQLite database, WAL files, instance secret, automatic backups) shall live in `/data`, declared as a `VOLUME`. Apart from that, the container is stateless and can be destroyed and recreated freely. | M | P1 |
| DEP-5 | The server shall listen on one HTTP port (default `8080`, `TAZAMUN_PORT`) on all interfaces. TLS is handled by a reverse proxy. When `TAZAMUN_TRUST_PROXY` is set, the client IP and protocol are taken from `X-Forwarded-*` headers. | M | P1 |
| DEP-6 | The image shall define a `HEALTHCHECK` that calls a built-in `tazamun healthcheck` subcommand (which hits `/v1/health`), so no `curl` or `wget` is needed in the image. | M | P1 |
| DEP-7 | On `SIGTERM` or `SIGINT` the server shall stop accepting connections, finish in-flight requests within 10 s, checkpoint the WAL and close the database. The entrypoint shall run the server directly (not via `npm`), so it receives signals as PID 1, or use a minimal init. | M | P1 |
| DEP-8 | Logs shall go to stdout/stderr, one event per line, with `TAZAMUN_LOG_FORMAT=json\|pretty` (default `json` in the image). | M | P1 |
| DEP-9 | Images shall be built for `linux/amd64` and `linux/arm64`. `linux/arm/v7` is a Could. | M | P1 |
| DEP-10 | The image shall carry standard OCI labels (`org.opencontainers.image.source`, `.version`, `.revision`, `.created`, `.licenses`, `.title`, `.description`). | S | P1 |
| DEP-11 | The image shall contain no secrets and no default credentials. If no instance secret is provided, one shall be generated into `/data` on first start (used e.g. for stable fake `prelogin` responses for unknown usernames, SEC-9). | M | P1 |

#### Configuration and administration

| ID | Requirement | Pri | Phase |
| -- | ----------- | --- | ----- |
| DEP-12 | All configuration shall come from environment variables prefixed `TAZAMUN_` (extends ADM-1), or from a JSON config file named by `TAZAMUN_CONFIG_FILE` whose keys are the same settings. An environment variable overrides the file, and the file overrides the default. Each secret-like variable shall also accept a `*_FILE` variant for Docker and Kubernetes secrets. | M | P1 |
| DEP-13 | Configuration shall be validated at startup against one schema. Invalid or missing required values, and unknown keys in the config file, shall stop the server with a message naming the variable or file key and the expected format. | M | P1 |
| DEP-14 | `TAZAMUN_PUBLIC_URL` is required. If it isn't `https://`, the server shall refuse to start unless the host is `localhost`/`127.0.0.1` or `TAZAMUN_ALLOW_INSECURE=true` is set. In that case it logs a warning on every start. | M | P1 |
| DEP-15 | The configuration reference in the documentation shall be generated from the config schema (one source of truth). CI shall fail if it's out of date. | S | P1 |
| DEP-16 | The image shall include an admin CLI: `tazamun invite create\|list\|revoke`, `tazamun backup <file>`, `tazamun restore <file>` (server must be stopped), `tazamun migrate --status`, `tazamun accounts list\|delete` (metadata only: ID, created, last seen, storage used; `delete` needs `--yes` and writes a backup first), `tazamun version`, `tazamun healthcheck`. Invites are single-use and expire after 7 days unless created with another `--expires`. Admin commands never migrate the database. | M | P1 |
| DEP-17 | Recommended container limits shall be documented and set in the example Compose files (baseline: 256 MB memory, 0.5 CPU). The server shall run correctly within them under PERF-7 load. | S | P1 |

#### Upgrades and backups

| ID | Requirement | Pri | Phase |
| -- | ----------- | --- | ----- |
| DEP-24 | Before applying migrations, the server shall write a consistent backup of the database to `/data/backups/pre-migrate-<from>-<to>.db`, keeping the last 3. Downgrading means restoring that backup with the older image. | M | P1 |
| DEP-25 | `tazamun backup` shall produce a consistent copy while the server is running (SQLite backup API or `VACUUM INTO`). `tazamun restore` shall verify integrity (`PRAGMA integrity_check`) before replacing the database, save the replaced database to `/data/backups/pre-restore-<time>.db`, and keep each account's `seq` counter at least as high as before, so `seq` never goes backwards. It shall give the data a new generation, so devices push back what the backup lacks (ENG-16). Fulfils ADM-6. | M | P1 |
| DEP-26 | Any 1.x release shall upgrade directly to any later 1.x release. Release notes shall mark breaking configuration changes, which are allowed only in a major version. | M | P6 |
| DEP-27 | Each server release shall accept clients down to the previous minor release (`minClientVersion`, section 4.4.1), because extension store updates reach users over several days. | M | P6 |

#### Build and publishing pipeline

| ID | Requirement | Pri | Phase |
| -- | ----------- | --- | ----- |
| DEP-28 | Images shall be built and published **only by CI** (GitHub Actions), never from a developer machine. | M | P1 |
| DEP-29 | Every pull request shall build the image (without pushing it) and run a **container smoke test**: start the container with a temporary `/data`, wait until healthy, run the API integration suite against it (create account, sign in, push, pull, revoke), stop with `SIGTERM`, then start again on the same `/data` and verify the data is still there. | M | P1 |
| DEP-30 | Every push to `main` shall publish `ghcr.io/proless/tazamun:edge` and `:sha-<short sha>`. | M | P1 |
| DEP-31 | Every SemVer tag `vX.Y.Z` shall publish `:X.Y.Z`, `:X.Y`, `:X` and `:latest`. Pre-release tags (`vX.Y.Z-rc.N`) publish only their exact tag and never move `latest`, `X` or `X.Y`. | M | P6 |
| DEP-32 | Release images shall also be mirrored to Docker Hub (repository name decided at P6), so users who can't use GHCR have an option. | S | P6 |
| DEP-33 | Multi-arch builds shall use Buildx, with native arm64 runners where available (QEMU emulation otherwise), and a build cache. | S | P1 |
| DEP-34 | Every image build shall be scanned for vulnerabilities (e.g. Trivy or Grype). A release shall fail on fixable Critical vulnerabilities. Results shall appear in GitHub code scanning. | M | P1 |
| DEP-35 | Release images shall include an SBOM (SPDX or CycloneDX) and SLSA build provenance as registry attestations. | S | P6 |
| DEP-36 | Release images shall be signed with keyless cosign (Sigstore, GitHub OIDC). The documentation shall show the `cosign verify` command with the expected identity and issuer. | S | P6 |
| DEP-37 | Base images shall be pinned by digest. Renovate or Dependabot shall propose updates to base digests and dependencies, and each update goes through DEP-29. | M | P1 |
| DEP-38 | Publishing shall use the workflow's `GITHUB_TOKEN` with only `packages: write` (plus `id-token: write` for signing and attestations). The Docker Hub token shall be a repository secret available only to the release workflow on tags. | M | P1 |
| DEP-39 | The release workflow shall also attach the extension store packages and the AMO source archive to the GitHub release, all built from the same tag (section 6.2). | S | P6 |
