## 5. Other Nonfunctional Requirements

### 5.1 Performance Requirements

Reference client: a mid-range laptop from 2022 or later. Reference server: 1 vCPU, 256 MB RAM, SSD.

| ID | Requirement |
| -- | ----------- |
| PERF-1 | A local tab change shall be visible on another online device within **90 s** (debounce + alarm period), and within **15 s** when the other device's popup or the dashboard is open (5 s debounce, then the open page checks every 5 s). |
| PERF-2 | *Removed* with send tab ([ADR-0011](../adr/0011-private-browsing-choice-and-no-send-tab.md)). |
| PERF-3 | Importing 50,000 history entries on first enable shall finish within **5 min** and keep the browser responsive (work in chunks, yield between them). |
| PERF-4 | History search over 100,000 entries shall return within **200 ms** in the extension and the dashboard (after the first index build). |
| PERF-5 | A steady-state sync with no changes shall cost one `GET /v1/info` request (< 2 KB) per alarm period. |
| PERF-6 | Idle, the extension shall use no measurable CPU between alarms, and its memory shall stay under **50 MB** excluding the history index. |
| PERF-7 | The reference server shall handle **50 accounts × 4 devices** with p95 API latency under **200 ms** and resident memory under **256 MB**. |
| PERF-8 | Typical server storage per account: tabs and extensions < 1 MB; bookmarks (5,000 nodes) about 3 MB; history (1 year, ~30,000 URLs) about 30–60 MB. The quota default (ADM-3) reflects this. |

### 5.2 Security Requirements

#### Threat model

| Adversary | Protected? |
| --------- | ---------- |
| Server operator, hosting provider, stolen database or backup | **Yes, for content.** They see only ciphertext. |
| Network attacker | **Yes.** TLS, plus E2EE underneath it. |
| Another account on the same server | **Yes.** Isolated by account, and AAD binds each record to its account. |
| Malicious server tampering with records (swapping, replaying, dropping) | **Partly.** AAD stops records being swapped between IDs and collections. Replaying an old version or withholding records can't be fully detected in v1 (see [section 6.5](<6. Other Requirements.md#65-known-limitations-and-open-questions>)). |
| Malicious server serving a modified dashboard | **No.** Whoever controls the server controls the dashboard's JavaScript. The extension is not affected, since it's installed from a store. Documented, and a reason to self-host. |
| Malware or a hostile extension on the user's device, or a compromised browser | **No.** Out of scope. |

**Metadata the server can see:** account and device IDs, device names (stored in plaintext so the dashboard can list them before decryption — see [section 6.5](<6. Other Requirements.md#65-known-limitations-and-open-questions>)), browser family, collection names, record counts and sizes, write times, IP addresses, and request timing. History record IDs are keyed HMACs, so the server can't see URLs, but it can see how many distinct URLs there are and when they change.

#### Requirements

| ID | Requirement |
| -- | ----------- |
| SEC-1 | Key derivation: **Argon2id**, default m = 64 MiB, t = 3, p = 1, 16-byte random salt, 64-byte output → `authKey` (first 32 bytes) and `KEK` (last 32 bytes). Parameters are stored per account, so they can be raised later. Clients reject parameters below these defaults, so they can never be lowered. The passphrase is normalized to Unicode NFC first ([ADR-0008](../adr/0008-crypto-implementation.md)). |
| SEC-2 | The account key (32 random bytes) is wrapped with AES-256-GCM under the KEK. Collection keys are derived from it with HKDF-SHA256 (`info = "tazamun/v1/enc/" + collection`). The history ID key uses `info = "tazamun/v1/id/history"`. HKDF uses an empty salt. The wrapped account key carries AAD `tazamun/v1/account-key\|<accountId>`. |
| SEC-3 | Every payload is encrypted with AES-256-GCM, a fresh 96-bit random nonce, and AAD `accountId \| collection \| recordId`. Nonces are never reused (random 96-bit nonces are safe at this project's volume). |
| SEC-4 | The server stores `SHA-256(authKey)` and compares it in constant time. Session tokens are stored as SHA-256 hashes. |
| SEC-5 | The extension keeps the unwrapped account key in `storage.local`, protected by the OS profile, when *remember on this device* is on, and otherwise in `storage.session` (in memory, cleared when the browser closes), so the extension is locked until the passphrase is entered again. The trade-off (convenience vs. a passphrase prompt on every browser start) is a user setting, defaulting to *remember on this device* ([ADR-0009](../adr/0009-device-names-and-key-storage.md)). The passphrase, the KEK and the auth key are never stored. |
| SEC-6 | No plaintext payloads, URLs, titles, keys, tokens or passphrases in logs, error reports or analytics. **There are no analytics.** |
| SEC-7 | Dependencies are pinned with a lockfile, checked by automated audits in CI, and limited in number. The crypto code lives in `packages/core/src/crypto` and has test vectors (reference Argon2id, RFC 5869, RFC 4231, Wycheproof AES-GCM, and Tazamun format vectors), run in Node, Chromium and Firefox. Argon2id comes from `hash-wasm`, everything else from Web Crypto ([ADR-0008](../adr/0008-crypto-implementation.md)). |
| SEC-8 | The dashboard sends a strict CSP, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`, and HSTS (behind TLS). |
| SEC-9 | The server applies rate limits to sign-in, account creation, prelogin and recovery, per IP and per account, and makes `prelogin` responses for unknown usernames look like real ones. |
| SEC-10 | A security review of the crypto and protocol (an external reviewer if possible) happens before 1.0. |

### 5.3 Privacy Requirements

| ID | Requirement |
| -- | ----------- |
| PRIV-1 | Private or incognito browsing is captured only by modules for which the user turned on *Include private windows* on that device. The switch is off by default and needs the browser to allow the extension in private windows ([ADR-0011](../adr/0011-private-browsing-choice-and-no-send-tab.md)). |
| PRIV-2 | Each module can be turned off per device. Turning a module off asks whether to delete that device's data for it from the server. |
| PRIV-3 | Users can exclude domains or URL patterns from tabs and history (examples ship with the extension, e.g. banking and health sites). |
| PRIV-4 | The extension contacts only the configured server. No third-party requests (no remote fonts or icons, no telemetry). Favicons are shown only from cached tab data or the browser's own favicon service. |
| PRIV-5 | A privacy policy (required by the extension stores) states exactly what is synced, what the server sees, and that the project itself collects nothing. |

### 5.4 Reliability and Data Safety

| ID | Requirement |
| -- | ----------- |
| REL-1 | No sync path may permanently destroy user data without a recoverable copy: bookmark snapshots (BMK-12), the mass-deletion guard (BMK-13), and tombstones with expiry. |
| REL-2 | Applying remote changes is idempotent. Applying the same batch twice gives the same result. |
| REL-3 | An interrupted sync (browser closed, service worker killed, network down) resumes from the outbox and the last confirmed `seq` without duplicating or losing changes. |
| REL-4 | Server writes are transactional. A batch is either fully stored with new `seq` values or not stored at all. |
| REL-5 | Upgrades: the server migrates automatically (ADM-4). Clients tolerate unknown payload fields and keep records with newer schema versions without applying them (ENG-10). |
| REL-6 | Merge functions are pure and covered by property-based tests (random concurrent edits on two or three simulated devices must converge to the same state). |

### 5.5 Software Quality Attributes

- **Maintainability:** TypeScript strict mode, ESLint and Prettier, one module per directory, the engine free of type-specific code, and an ADR for every decision that's hard to reverse.
- **Testability:** the core library runs in Node, so merge, crypto and protocol tests need no browser. The browser APIs are hidden behind interfaces with in-memory fakes.
- **Portability:** one extension codebase; the server is one container for amd64 and arm64.
- **Usability:** a first-time user completes onboarding and sees tabs from a second browser in **under 5 minutes** without reading documentation.
- **Accessibility:** WCAG 2.1 AA for the popup, options page and dashboard.
- **Priority order when attributes conflict:** data safety > security and privacy > correctness > usability > performance > features.
