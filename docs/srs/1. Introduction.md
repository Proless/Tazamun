## 1. Introduction

> **Revision 2 (2026-11-24).** This revision reworks the SRS around the "one place" positioning. It supersedes revision 1, whose server resolved conflicts (so it had to read user data) and which required .NET, Node.js and MySQL. Every key decision is recorded as an ADR in [`adr/`](../adr/README.md).

### 1.1 Purpose

This Software Requirements Specification (SRS) defines the functional and non-functional requirements of **Tazamun** release 1.0.

The intended audience is open-source contributors: developers, testers and people who self-host. This SRS is a non-binding reference for the community. It sets the baseline that Tazamun 1.0 should meet, and it changes through pull requests like the code.

**Disclaimer:** Parts of this SRS were drafted with the help of AI. Every line was reviewed and corrected by a human.

### 1.2 Product Vision

People who use more than one browser end up with a pile of tools: one extension and account to sync bookmarks, another for tab sessions, maybe a third for history, and nothing at all to track which extensions they've installed where. Each tool has its own setup, backend and failure modes.

> **Tazamun is one extension, one account, and one place for your browser data across Chrome, Edge and Firefox. It's end-to-end encrypted and self-hostable.**

Bitwarden is a useful analogy: one vault for every password, whatever device you're on. Tazamun is one vault for your browser state, whichever browser you're in.

#### Goals

| ID | Goal |
| -- | ---- |
| G1 | **One install, one account.** A single extension and a single account cover every supported data type. |
| G2 | **One place.** A web dashboard shows and manages all synced data from every browser together. |
| G3 | **Private by design.** The server stores only ciphertext and never needs plaintext to work (end-to-end encryption). |
| G4 | **Self-hostable in minutes.** One container and one data volume. No external database. |
| G5 | **Easy to extend.** Adding a new data type means writing a small module, not a new subsystem. |
| G6 | **Safe.** Sync must never silently destroy user data. Destructive changes can be recovered from. |

#### Non-Goals (v1.0)

- Syncing passwords, cookies, logged-in sessions, form data or browser settings. Mostly there is no extension API for these; where there is, password managers do it better.
- Safari, and Chrome or Edge on mobile (no extension support for Tazamun's needs). Firefox for Android is a post-1.0 stretch goal.
- Becoming a full bookmark manager (tagging, read-later, archiving), or sharing data between users.
- A hosted "Tazamun cloud" run by the project. Users self-host, or use an instance someone else runs.

### 1.3 Scope of Release 1.0

- **Browsers:** Google Chrome, Microsoft Edge and Mozilla Firefox on desktop (Windows, macOS, Linux).
- **Data types:** open tabs, browsing history, bookmarks, and an inventory of installed extensions.
- **Components:** one browser extension (one codebase, three build targets), a sync server, a web dashboard, and a shared core library. See [section 2.2](<2. Overall Description.md#22-architecture>).

### 1.4 Definitions, Acronyms and Abbreviations

| Term | Definition |
| ---- | ---------- |
| Account | A user's identity on a Tazamun server. People sign in with a username; internally it's a random account ID. No email address. |
| Account key | A random 256-bit key that encrypts all of an account's data. The server stores it only in wrapped (encrypted) form. |
| ADR | Architecture Decision Record. A short document recording one design decision and why it was made. |
| Collection | A named group of records of one data type, e.g. `tabs`, `history`, `bookmarks`, `extensions`, `devices`, `commands`. |
| Compose | Docker Compose (v2): a YAML file describing the containers, volumes and networks of a deployment. |
| Device | One browser profile with Tazamun installed. Two profiles in the same Chrome are two devices. |
| Echo | A browser event fired because Tazamun itself just applied a remote change. It must not be treated as a new local change. |
| E2EE | End-to-end encryption. Data is encrypted on the client and only clients hold the keys. |
| GHCR | GitHub Container Registry (`ghcr.io`), the primary registry for Tazamun images. |
| HLC | Hybrid Logical Clock. A timestamp combining wall-clock time and a counter, used to order edits across devices. |
| KEK | Key-encryption key. Derived from the user's passphrase and used only to wrap the account key. |
| OCI image | A container image in the Open Container Initiative format, runnable by Docker, Podman and Kubernetes. |
| Mirror | The extension's local copy of the last synced state, used to tell local changes from remote ones. |
| Module | The code that syncs one data type: it reads browser changes, maps them to records, and applies records back to the browser. |
| MV3 | Manifest V3, the current WebExtension platform version. |
| Pairing | Connecting a new device to an existing account. |
| Recovery key | A random key, shown once at sign-up, that sets a new passphrase when the old one is lost (ACC-5). |
| Record | The unit of sync: an ID, a server sequence number, and an encrypted payload. |
| Seq | A monotonically increasing number the server assigns to every record write, used for incremental pulls. |
| SBOM | Software Bill of Materials: a machine-readable list of everything inside an image. |
| Snapshot | A full local backup of one data type (mainly bookmarks), taken before risky changes are applied. |
| Tombstone | A record marking that an item was deleted, so the deletion propagates to other devices. |
| SRS | Software Requirements Specification. |

**Requirement IDs** use a feature prefix plus a number (e.g. `TAB-3`). Each requirement has a priority and a project phase:

- **Must:** required for 1.0.
- **Should:** expected for 1.0; can slip with a documented reason.
- **Could:** nice to have; post-1.0 if time runs out.

Phases (P0–P6) match the roadmap in [`CLAUDE.md`](../../CLAUDE.md). Reference requirement IDs in commits and pull requests.
